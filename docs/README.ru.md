# Pecia — минималистичный текстовый редактор

---

**[⬇️ Скачать последнюю версию (1.0.0)](https://gitee.com/qiuzongman/pecia/releases/download/1.0.0/Pecia_x64_1.0.0.zip)**

Легковесный текстовый редактор для Windows на базе C++17 + FLTK. Много вкладок, мгновенное открытие больших файлов, поддержка множества кодировок, расширение скриптами на Lua.

> **Платформа**: поддерживается только **Windows x64 (64 бит)**. 32-битная версия не предоставляется, кроссплатформенная поддержка (Linux/macOS/32 бита) более не ведётся. Скрипты сборки включают проверку на 64-битность (см. начало CMakeLists); при ошибочной конфигурации 32 бит будет выдана ошибка.

## Быстрый старт

### Требования к среде (помимо исходного кода и сторонних библиотек)

- Windows 10/11 x64 (1803+; встроенные утилиты curl/tar)
- **Visual Studio Build Tools 2022 / VS2022** (с рабочей нагрузкой «Разработка на C++ для Windows»)
  - Скрипт `build/msvc_env.bat` **автоматически определяет** MSVC и Windows SDK (не зависит от vcvars/vswhere/командной строки разработчика; обычный cmd подойдёт). Также можно указать кастомные пути через переменные окружения `PECIA_MSVC_ROOT` / `PECIA_SDK_ROOT`.
- **CMake ≥ 3.16** (должен быть в PATH; генератор — **NMake Makefiles**, Ninja не нужен)
- **Цепочка инструментов Rust** (≥ 1.85, edition 2024; для компиляции FFI-библиотек mmdr и RaTeX; устанавливается через https://rustup.rs; первая сборка требует подключения к интернету для загрузки зависимостей из crates.io)
- **Подключение к интернету** (только при первой сборке: `2_download.bat` загружает зависимости, `4_build_rust.bat` выполняет `cargo fetch`)
- **git не требуется** (зависимости загружаются через curl и распаковываются tar)

### Сборка (рекомендуется: один двойной клик)

```bat
REM После скачивания исходного кода просто дважды щёлкните по этому скрипту.
REM Он последовательно выполняет: 1 проверка цепочки инструментов → 2 загрузка 6 сторонних библиотек → 3 применение патчей →
REM 4 cargo fetch + сборка двух Rust FFI → 5 сборка FLTK + CMake сборка Pecia →
REM запуск 14 unit-тестов.
REM Время первой сборки зависит от сети и мощности ПК; повторные сборки используют кэш, инкрементальная сборка + тесты занимают ~1-2 минуты.
build\full.bat
```

### Сборка (пошагово, пять скриптов с номерами)

Скрипты в `main/build/` имеют узкую специализацию и могут быть перезапущены по отдельности:

```bat
REM ① Только чтение: проверка cmake/cargo/cl/nmake/rc/tar/curl; host Rust должен быть msvc
build\1_check_env.bat

REM ② Загрузка + распаковка сторонних библиотек в .thirdparty/ (идемпотентно; при наличии — пропуск)
build\2_download.bat

REM ③ Одностороннее применение патчей из main/patches/ в .thirdparty/ (идемпотентно)
build\3_patch.bat

REM ④ cargo fetch для загрузки зависимостей Rust + cargo build --release для сборки двух FFI-статических библиотек
REM   (этот шаг легко забыть: Rust тоже нужно компилировать, а не использовать готовые бинарники)
build\4_build_rust.bat

REM ⑤ Сборка FLTK + Pecia, запуск ctest
build\5_build_pecia.bat

REM ★ Общий вход = ②→③→④→⑤ (эквивалентно двойному клику full.bat)
build\full.bat
```

> При изменении только кода достаточно дважды щёлкнуть `5_build_pecia.bat` — он сам синхронизирует патчи
> и при необходимости вызовет `4_build_rust.bat`.

> Сторонние библиотеки (FLTK/Lua/PCRE2/md4c/litehtml/stb) загружаются автоматически
> скриптом `2_download.bat` по адресам из `build/deps.txt` в `.thirdparty/` в корне проекта;
> адреса можно редактировать вручную (deps.txt). Rust-библиотеки (mmdr/RaTeX/resvg и др.)
> загружаются cargo из crates.io (версии фиксируются в Cargo.lock FFI-крейтов).
> Модификации FFI-обёрток и т.п. хранятся в `main/patches/` и выкладываются вместе с исходным кодом.

### Запуск тестов

Скрипты сборки автоматически запускают unit-тесты (ctest, включая проверку согласованности документации test_docs). Отдельный запуск:

```bat
REM Каталог сборки: temp\cmake_build\ в корне проекта; исполняемые файлы — в build\
ctest --test-dir ..\..\temp\cmake_build --output-on-failure
```

> Также можно запустить `build\5_build_pecia.bat`, который автоматически выполнит ctest после компиляции.
> **Тесты — ворота сборки**: при падении любого теста скрипт завершается через `exit /b 1`, `full.bat` прерывается,
> сообщение «всё выполнено» не выводится. Для быстрой сборки без тестов установите `PECIA_SKIP_TESTS=1`.
> (Скрипты написаны для Windows cmd и должны сохраняться с окончаниями строк **CRLF, иначе парсинг будет некорректным.)

### Упаковка релиза

```bat
build\pack.bat
```

Вывод в `release/` в корне проекта (`release/<версия>/` и `Pecia-<версия>.zip` с LICENSE и THIRD-PARTY-NOTICES.md). В каталоге `main/` релизные артефакты не хранятся.

## Обзор архитектуры

> Ниже описана реальная архитектура и потоки данных **текущего исходного кода** (C++17 + FLTK 1.4.5).
> Описание каталогов и модулей приведено в файле «目录结构说明.md».

### I. Исполняемые программы и модель процессов

Продукт поставляется как **1 основная программа + 2 отдельных инструмента**, все три разделяют значительную часть исходного кода core/ui:

| Исполняемый файл | Точка входа | Назначение | Одиночный экземпляр |
|---|---|---|---|
| `Pecia.exe` | `main.cpp` | Основной текстовый редактор | Может быть запущен несколько раз (каскадирование `PECIA_POS`) |
| `PeciaLua.exe` | `LuaTool/main_lua.cpp` | Автономная консоль Lua для запуска скриптов над основным документом | Да (`MUTEX_LUA_TOOL`) |
| `PeciaAIChat.exe` | `AIChat/main_ai.cpp` | Автономное окно AI-чата, читает выделение из основного документа | Да (`MUTEX_AI_CHAT`) |

Все три компонента общаются через **именованные каналы** (формат кадра: `4 байта tag + u32 little-endian длина + нагрузка`, см. `core/PipeProtocol.h`). Основная программа запускает `LuaPipeServer`, whose `listenLoop()` в фоновом потоке слушает канал `\\.\pipe\pecia-lua-<pid>` для каждого процесса; при поступлении запроса диспетчеризует его в UI-поток через `Fl::awake`, затем возвращает кадр OK/ERR. `PeciaLua` / `PeciaAIChat` запускаются основной программой через `launchTool()`, имя канала и язык передаются через командную строку.

### II. Уровни и направление зависимостей

Принудительное направление зависимостей (определено также в «目录结构说明.md»):

```
core  ←  editor  ←  ui
core  ←  script  ←  ui
test  может зависеть от любого уровня, но тестирует только чистую логику (без GUI)
```

- **`core/` (чистая логика, FLTK/UI запрещены)**: Config, CrashReport, I18n, Theme, SearchCore, EncodingCore, FileManager, ShortcutCore, OpLog, AiApiClient (фоновый HTTP-поток), PipeClient, UiBridge (интерфейс инверсии зависимостей).
- **`editor/`**: Document (модель — обёртка над Fl_Text_Buffer + ввод/вывод файлов + кодировка), Editor (расширение Fl_Text_Editor: подсветка строк/URL/пробельных символов/автоотступы).
- **`ui/`** (единственный уровень, где допустимо создавать Fl_Window / диалоги): MainWindow и распределённые по функциональности `MainWindow_*.cpp`, диалоговые окна, таблицы меню, горячие клавиши, подключение панели предпросмотра.
- **`script/`**: LuaEngine (не песочница — стандартная библиотека открыта полностью; модель доверия описана в `lua_api.txt`; включает scratch buffer + rex/win API), ScriptManager (сканирование/мета-информация/folder.ini), LuaParamParser (объявление параметров --!param).
- **`mdview/`**: Предпросмотр Markdown (md4c→HTML → рендеринг litehtml; mermaid/LaTeX рендерятся в процессе через Rust FFI); статически подключаемые产物 `mmdr_ffi` / `ratex_ffi`.

**`UiBridge` — единственная точка соединения core и UI**: `core/UiBridge.h` определяет чисто виртуальные методы `message()/confirm()`; `ui/UiBridge.cpp` предоставляет конкретную реализацию, инжектируемую через `setUiBridge()`. Таким образом `Document`/`FileManager` (core) при взаимодействии с пользователем вызывают только `uiBridge()->confirm(...)` и не зависят от каких-либо классов FLTK, что обеспечивает тестируемость ядра.

### III. Конфигурация / интернационализация / обработка сбоев

- **Конфигурация**: `settings.ini` (рядом с exe), чтение/запись через `core/Config.cpp`; механизм белого списка для записи применяется к конфиденциальным ключам AI. `recent file.ini` хранит список последних файлов.
- **Интернационализация**: `lang/en.ini`, `lang/zh-CN.ini`, загрузка через `core/I18n.cpp`; наборы ключей в обоих файлах должны совпадать (проверяется test_docs).
- **Обработка сбоев**: `core/CrashReport.cpp` используется всеми тремя exe; дампы пишутся в `temp/` рядом с exe (dmp + лог стека + хвост последнего журнала операций); хранятся последние 3 dmp, очистка за 7 дней.

### IV. Основные подсистемы: редактирование / скрипты / предпросмотр

- **Многостраничное редактирование**: `MainWindow` управляет `m_tabsList` (вкладка = редактор + документ); при переключении/закрытии сначала вызывается `buffer(nullptr)`, затем удаление doc — это предотвращает обращение колбэков FLTK к уже уничтоженному буферу.
- **Запуск скриптов**: `LuaEngine` работает над **снимком документа** (не песочница, стандартная библиотека полностью открыта; доступ через именованный канал, канал ограничен DACL текущего пользователя); результат записывается обратно через `applyDocumentSnapshot`. Меню скриптов формируется из `script/scripts/**` (содержит `.lua` + `folder.ini` с переводами имён); при сборке копируется в `build/script/`.
- **Предпросмотр Markdown**: редактирование → `ui/MainWindow_preview.cpp`; `mdview/preprocess` конвертирует вывод md4c в HTML, извлекает блоки ```` ```math ```` для RaTeX (SVG), блоки mermaid для mmdr (PNG); `mdview/container` — адаптер document_container для litehtml; `PreviewPanel` отвечает за цепочку рендеринга. Автообновление предпросмотра по интервалам (1с/5с/10с/30с).

### V. Сборка и тестирование

- **Пять скриптов с номерами + общий вход** (`main/build/`, узкая специализация, каждый скрипт можно перезапускать отдельно):
  - `full.bat`: **общий вход** (двойной клик), последовательно вызывает ②→③→④→⑤.
  - `1_check_env.bat`: проверка цепочки инструментов (только чтение; cmake/cargo/cl/nmake/rc/tar/curl; `rustc -vV` должен указывать host `pc-windows-msvc`, иначе не удастся собрать линкуемый `.lib`).
  - `2_download.bat`: загрузка + распаковка сторонних библиотек в `.thirdparty/` по `deps.txt` (идемпотентно).
  - `3_patch.bat`: синхронизация патчей (`main/patches/ → .thirdparty/`, **одностороннее** принудительное перезаписывание).
  - `4_build_rust.bat`: `cargo fetch` для загрузки зависимостей Rust → `cargo build --release` для сборки `mermaid_ffi.lib` / `ratex_ffi.lib` (**Rust тоже нужно компилировать**, не пропускайте этот шаг).
  - `5_build_pecia.bat`: по временным меткам определяет, нужно ли пересобирать FLTK / два Rust FFI → конфигурация NMake и **инкрементальная** сборка (используется кэш `temp/cmake_build`; полная пересборка только если кэш создан другим генератором) → автоматический запуск ctest.
  - `_common.bat`: общие переменные путей скриптов, разрешение абсолютных путей `tar`/`curl`, загрузка окружения MSVC и подпрограмма `:fetch_rust_deps`.
- `build/msvc_env.bat`: определение MSVC и Windows SDK, настройка `PATH`/`INCLUDE`/`LIB` (приоритетно использует `vswhere.exe` для поиска любого пути установки; общий для всех скриптов сборки).
- `build/pack.bat`: упаковка содержимого `build/` в `release/<версия>/`.
- `build/deps.txt`: список загрузок сторонних библиотек (`имя=URL|файл-индикатор`, чистый ASCII — китайские комментарии приводят к сбою `for /f` при парсинге в кодировке GBK).
- **Unit-тесты** (`test/`, только чистая логика ядра): search/encoding/config/document/match_highlight/param/docs/lua_engine (включая rex-регулярки)/undo/script_manager/pipe/shortcut/ui_smoke/ui_tool_smoke — итого **14** целей,ctest — все зелёные + `test_docs` — проверка согласованности документации.

> Модификации исходного кода сторонних библиотек всегда хранятся в `main/patches/` и автоматически применяются к `.thirdparty/` при сборке; обратное перезаписывание запрещено (подробнее см. AGENTS.md). Предупреждения компиляции сторонних библиотек не засчитываются в «нулевое количество предупреждений /W4» основной программы (ограничение распространяется только на исходный код первого уровня в `main/`).
