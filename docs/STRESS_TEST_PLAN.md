# Pecia 压力测试计划（STRESS_TEST_PLAN.md）

> 目的：**发版前确认"不会被真实数据打穿"**。功能测试证明"点得通"，压力测试证明"量大也不塌"。
> 本计划只管非功能面（性能、资源、稳定性、边界），功能正确性由 `ctest` 的 27 个门禁负责。
> 执行人按节顺序做完，把结果填进最后一节的记录表；**任何一项判据不满足，先定性归因再决定是否阻塞发版**。

## 一、环境与记录方式

| 项 | 要求 |
|---|---|
| 被测程序 | `build/Pecia.exe`（构建产物目录，不是 `main/`） |
| 系统 | Windows 10/11 x64，**记录显示器分辨率与缩放比例**（100%/150% 结果不同） |
| 记录工具 | 任务管理器（内存/CPU/句柄/GDI 对象）、`PECIA_PROFILE=1` 性能日志 |
| 性能日志位置 | 预览打点写在 **exe 同级的 `preview_profile.log`**（每次渲染覆盖）；`%TEMP%\pecia_pp_profile.log` 记 parse 阶段 |
| 样本 | `example/ex2.LargeFile/`（大纯文本）、`example/ex3.LargeMarkdown/`（大 Markdown）、自己的真实文档各 1 篇 |
| 判定纪律 | **同一台机器、同一版本、同一缩放比**下比较；跨机器数字只作参考，不作结论 |

启动性能日志的方式：设环境变量 `PECIA_PROFILE=1` 再启动 exe，或在已开启的会话里从菜单打开预览均可（每次渲染会追加/覆盖打点）。

## 二、样本准备

```bat
REM 大 Markdown（ex3）：双击对应 bat 生成，产物不入库
cd main\example\ex3.LargeMarkdown
100kb.bat      1mb.bat      5mb.bat

REM 大纯文本（ex2）：500MB / 1.5GB，生成较久
cd main\example\ex2.LargeFile
50mb.bat       500mb.bat      1500mb.bat
```

**尺寸与渲染路径的对应关系**（关键：阈值判的是**渲染后 HTML 字节数**，不是 `.md` 字节数；中英混排实测膨胀约 1.55 倍）：

| 样本 | md 大小 | 渲染后 HTML | 走的路径 |
|---|---|---|---|
| `100kb.md` | 100 KB | ≈ 160 KB | 全量（未过 256 KB 阈值） |
| `1mb.md` | 1 MB | ≈ 1.6 MB | 分块，130 块 |
| `5mb.md` | 5 MB | ≈ 8 MB | 分块，647 块（极端） |

三档里只有 `100kb` 走全量路径，其余两档走分块——**不要只看大文件，小文档变慢才是回归**。
（原先还有一档 `200kb`，渲染后 ≈ 320 KB 刚跨过 256 KB 阈值，专门用来做"全量 vs 分块"
的 A/B 对照；2026-10-24 精简样本时删掉了。要复现这一档：照 `100kb.bat` 复制一份，
把 `TARGET_BYTES` 改成 `204800` 即可。）

### 样本内容骨架与可调参数

`gen_large_md.ps1` 生成的每一节固定包含：二级标题、中英混排段落、行内代码/粗体/斜体/
删除线/链接、一个**必须折行的超长不可断词 URL**（用于测折行与横向滚动）、三级嵌套列表、
引用块、4 列表格、围栏代码块，以及一张指向 `../ex1.markdown/sample-png.png` 的本地图片。
所以 `ex1.markdown/` 与 `ex3.LargeMarkdown/` **要一起保留**，单独拷走 ex3 会看到图片占位符。

大纲与目录跳转需要真实层级：每 `-SectionsPerChapter`（默认 12）节插一个一级标题，
全是同级标题就测不出层级。要自定义尺寸或层级，直接调脚本：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\gen_large_md.ps1 `
    -OutFile .\custom.md -TargetBytes 3000000 -SectionsPerChapter 12
```

产物为 UTF-8 无 BOM + CRLF，与 Windows 编辑器写出的文件一致；`5mb.md` 生成需十几秒到
一分钟（取决于磁盘）。

## 四、基线（2026-10-23 实测，供回归对照）

环境：本机 Windows，`PECIA_PROFILE=1`，预览首次渲染，`build/Pecia.exe` = 1.1.0。
样本：`example/ex3.LargeMarkdown/`，与本机文档同盘。

| 样本 | 路径 | 预处理 | parse / split | 首屏 layout | draw | 峰值工作集 |
|---|---|---|---|---|---|---|
| `100kb.md` | 全量 | 5.4 ms | parse **198.6 ms** | 22.9 ms | 22.3 ms | 91 MB |
| `200kb.md` | 分块（26 块） | 9.0 ms | split 17.2 ms | 42.9 ms | 5.0 ms | 47 MB |
| `1mb.md` | 分块（130 块） | 47.5 ms | split 111.5 ms | 45.6 ms | 8.0 ms | 68 MB |
| `5mb.md` | 分块（647 块） | 757.1 ms | split 429.7 ms | 44.5 ms | 5.0 ms | 185 MB |

**读数解读（重要）**：

1. **首屏成本 = 预处理 + split + 首窗口**，与文档大小近似线性；`draw` 恒定很小。
2. **`100kb` 反而比 `200kb` 慢约 4 倍**——这是已知的阈值错位：`100kb.md` 的 HTML 只有 160 KB，
   没到 256 KB 阈值，走全量渲染（`parse` 198ms 一次性建整棵 DOM）；`200kb.md` 越过阈值后只排版首个窗口。
   所以 **100~165 KB 这一档 md 是全项目体验最差的区间**。是否调整阈值属产品决策
   （代价：分块模式的总高度是估算值，滚动条会先估后修正），**发版前不改**，仅记录。
3. **5 MB 文档 1.2 秒首屏、185 MB 内存**，属可接受；`preprocess` 757 ms 是主要成本，其次是 `split` 430 ms。
4. 峰值工作集在**全量路径**上更高（91 MB vs 分块 47 MB），因为整棵 DOM 常驻。

### 4.1 侧栏大纲的绘制成本（`test_mainwindow_smoke` 实测，非预览副作用）

大纲面板是自绘树，每条标题都要量一次文本宽度（本机 `fl_width` 约 65 µs/次），
所以**成本必须只跟可见行数有关**：

| 大纲条数 | 修复前（全量遍历） | 修复后（只画视口内） |
|---|---|---|
| 200 条 | 46 ms | 13 ms |
| 5000 条（≈ `5mb.md` 的 5498 条） | **2600 ms** | **7.5 ms** |

> 修复前每次重绘（滚动一屏、点一次大纲条目）都卡 1~3 秒；修复后与文档大小无关。
> 绝对值随机器浮动，`test_mainwindow_smoke` 守的是 **5000 行 / 200 行 的比值**
> （≤ 3 倍 + 50 ms 余量），不守死毫秒数。

**同一次实测里其余几段成本**（5 MB 文档、5498 条大纲，本机）：

| 工序 | 耗时 | 说明 |
|---|---|---|
| `setOutline` 建行表（5000 行） | 1.2 ms | 行模型是定高行，滚动条量程精确，无需分级加载 |
| 点击条目 → 块表扫描找锚点 `anchor(scan blocks)` | 0.4 ms | 扫 647 块 HTML 全文，`std::string::find` 够快，不需要 id 索引 |
| 点击条目 → 目标块 layout + 块内精确定位 `anchor(layout+find)` | 23 ms | litehtml 排一块 12 KB，**这是点击成本的主体** |
| 点击后首帧绘制 `draw` | 30 ms | 新窗口两块排版 + 绘制 |

> 后两项是「跳转必须精确到元素」的固有代价（不排版就不知道标题在块内第几像素），
> 与大纲行数无关，也无法用行级虚拟化消掉。整次点击 ≈ 53 ms，属即时响应。
> 上面的 `anchor(...)` 三条打点在 `PECIA_PROFILE=1` 时写入 `preview_profile.log`。

### 4.2 首轮自动化结果（2026-10-23，预览开启，单次启动取峰值）

极限结构用例（对应 §三 C 组）与 50 MB 纯文本（B1）已跑过一轮，样本见 `temp/stress/`（临时，不入库）：

| 样本 | 内容 | 结果 | 峰值工作集 |
|---|---|---|---|
| `c1_nest.md` | 2000 层嵌套引用 + 1000 层嵌套列表 | **存活，预览完成** | 37 MB |
| `c1b_div_1000.md` | raw HTML `<div>` 嵌套 1000 层 | **存活**（litehtml 深嵌套防护生效） | 36 MB |
| `c1b_div_2000.md` / `_5000.md` | 同上 2000 / 5000 层 | **存活** | 28 MB |
| `c2_longline.md` | 单行 1 MB 无空格 | **存活**，draw 56 ms | 185 MB |
| `c3_wide_table.md` | 200 列 × 30 行表格 | **存活** | 77 MB |
| `c4_many_images.md` | 200 张本地图片引用 | **存活** | 36 MB |
| `c8_binary.md` | 100 KB 二进制垃圾当 .md 打开 | **存活**，未进预览（按非 Markdown 处理） | 22 MB |
| `ex2.LargeFile/50mb.txt` | 50 MB 纯文本 | **存活**，标题正确，累计 CPU 1.58 s | 80 MB |

> 结论：**深嵌套不再触发栈溢出**（历史上 `<div>` 千层会 `0xC00000FD`，现在被 litehtml 的深嵌套防护挡住）。
> 唯一偏高的是「单行 1 MB」的 185 MB 内存——那是一行内被拆成极多行内盒的必然代价，属可接受。

复现方式：把下面这段贴进终端（需已生成样本）。

```powershell
$env:PECIA_PROFILE='1'
$exe='E:\tmp\AI.Agent\Pecia\build\Pecia.exe'
$log='E:\tmp\AI.Agent\Pecia\build\preview_profile.log'
$dir='E:\tmp\AI.Agent\Pecia\main\example\ex3.LargeMarkdown'
foreach($n in @('100kb','1mb','5mb')){
  if(Test-Path $log){Remove-Item $log -Force}
  $p=Start-Process $exe -ArgumentList (Join-Path $dir "$n.md") -PassThru
  Start-Sleep -Seconds 6; $p.Refresh()
  "$n peakWS=$([math]::Round($p.PeakWorkingSet64/1MB,0))MB cpu=$([math]::Round($p.TotalProcessorTime.TotalMilliseconds,0))ms"
  if(!$p.HasExited){Stop-Process -Id $p.Id -Force}
  if(Test-Path $log){Get-Content $log}
}
```

### 5.1 本轮压力测试新发现（2026-10-23，均为实测，未修）

| # | 现象 | 根因（已定位到代码） | 影响面 | 建议 |
|---|---|---|---|---|
| N1 | 命令行传 >2 GB 文件：静默忽略，无提示 | `editor/Document.cpp` 用 `long sz = ftell(fp)`，MSVC 的 `long` 是 32 位，>2 GB 溢出成负数 → 走 `if (sz < 0) return false`，永远到不了"文件过大"的提示分支 | 只在 >2 GB 触发；2.0–2.147 GB 仍会正常提示 | 改用 `_ftelli64` / `_fseeki64`，单点改动 |
| N2 | 只读文件保存：无提示、文件未变、文档仍标脏 | `saveWithEncoding` 写临时文件成功，`MoveFileExW(MOVEFILE_REPLACE_EXISTING)` 覆盖只读目标失败 → 返回 false；`MainWindow::doSave()` 对 false 不做任何 UI 反馈（`error.title` 只在临时文件都开不出来时弹） | 只读文件、ACL 拒绝、目标被占用 | `doSave`/`doSaveAs` 失败时统一弹一次错误框 |
| N3 | 反复开关预览，GDI 对象线性增长（每 10 次 +5，80 次 66→116） | 未定位（预览面板销毁路径；句柄与工作集稳定，只有 GDI 单调增长） | 长会话多次切预览；GDI 上限 1 万，短期无感 | 查 `PreviewPanel` 析构与 `WindowShadow` 的 DC/位图释放 |

## 六、执行顺序

1. **A（大 Markdown）→ B（大文本）**：核心能力，先跑；
2. **C（极限结构）→ D（多标签）**：容易暴露崩溃，早发现早止损；
3. **E（长时）→ F（异常）**：需要挂机与特殊环境，排在中间；
4. **G（脚本）→ H（打包更新）**：最后跑，H 必须在打包产物上做；
5. 全部通过后按 `docs/RELEASE_CHECKLIST.md` 走发版。
